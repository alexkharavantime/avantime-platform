# Strapi CMS pilot on DEV/staging

How to run the CMS pilot ([CMS_PILOT.md](./CMS_PILOT.md)) on a DEV/staging host next to the platform
staging stack ([STAGING_DEPLOYMENT.md](./STAGING_DEPLOYMENT.md)). Production is out of scope.

## Topology

| Component      | Where                                                                         | Exposure                                                                      |
| -------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Caddy (edge)   | `docker-compose.staging.edge.yml`, `docker/caddy/Caddyfile.staging`           | `:80` (redirect) and `:443` for `STAGING_SITE_HOST` and `STAGING_CMS_HOST`    |
| web            | `docker-compose.staging.yml`                                                  | only through Caddy (plus `127.0.0.1:${STAGING_WEB_PORT}` for operators)       |
| Strapi         | CMS repository, `docker-compose.staging.yml` (project `avantime-cms-staging`) | only through Caddy; admin optionally limited by `STAGING_CMS_ALLOWED_CLIENTS` |
| CMS PostgreSQL | same CMS project, internal network                                            | none (no published port)                                                      |
| CMS media      | volume `avantime-cms-staging_cms_uploads`                                     | `https://<cms-host>/uploads/…` (public by URL)                                |
| Snapshots      | volume `avantime-staging_staging-cms-snapshots`                               | none                                                                          |

web and Strapi share the internal external network `CMS_EDGE_NETWORK` (default
`avantime-staging-cms-edge`): the site reads the CMS at `http://cms:1337`, the CMS sends its webhook to
`http://web:3000/api/cms/revalidate`. Caddy answers `404` to the webhook path from the internet. On
that network Caddy also carries the alias of the CMS host, so `next/image` fetches media from
`https://<cms-host>` through the edge instead of through the host's public address.

The CMS has its own database, media volume and secrets; nothing is shared with the platform
database, Redis or object storage.

## Parameters

| Parameter                                       | Where                  | Notes                                                                                                                                       |
| ----------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `STAGING_SITE_HOST`, `STAGING_CMS_HOST`         | platform staging env   | DNS A/AAAA records to the host; ports 80/443 open                                                                                           |
| `STAGING_TLS`                                   | platform staging env   | ACME e-mail (public DNS) or `internal` (closed network; add `docker-compose.staging.edge-internal-ca.yml`, clients must trust Caddy's root) |
| `STAGING_CMS_ALLOWED_CLIENTS`                   | platform staging env   | CIDRs allowed to the CMS admin/API; media stay public                                                                                       |
| `AUTH_PUBLIC_ORIGIN`, `APP_URL`, `APP_BASE_URL` | platform staging env   | `https://<site-host>`; `AUTH_PUBLIC_ORIGIN` is also the origin of the absolute canonical/hreflang URLs                                      |
| `CMS_*`                                         | platform staging env   | from `.local/platform-cms.staging.env` of the CMS repository; `CMS_MEDIA_URL` is also a build argument                                      |
| CMS secrets                                     | CMS `.env.staging`     | generated by `scripts/init-staging-env.sh`; keep in the secret store                                                                        |
| `CMS_BACKUP_DIR`                                | backup job environment | path covered by the host backup (see below)                                                                                                 |

## First deployment

```bash
# 1. CMS repository: secrets (refuses to overwrite), shared network, CMS stack
bash scripts/init-staging-env.sh https://<site-host> https://<cms-host>
docker network create --internal avantime-staging-cms-edge
docker compose --env-file .env.staging -f docker-compose.staging.yml up -d --build --wait
docker compose --env-file .env.staging -f docker-compose.staging.yml exec cms \
  npx strapi admin:create-user --firstname=… --lastname=… --email=… --password=…
CMS_ENV_FILE=.env.staging CMS_COMPOSE_FILE=docker-compose.staging.yml bash scripts/create-platform-token.sh
docker compose --env-file .env.staging -f docker-compose.staging.yml exec cms node scripts/seed-pilot.js

# 2. Platform: merge .local/platform-cms.staging.env into the staging env file, then
docker compose --env-file "$STAGING_ENV_FILE" -p avantime-staging \
  -f docker-compose.staging.yml -f docker-compose.staging.edge.yml build   # CMS_MEDIA_URL is baked in
# backup + migration as in STAGING_DEPLOYMENT.md, then
docker compose --env-file "$STAGING_ENV_FILE" -p avantime-staging \
  -f docker-compose.staging.yml -f docker-compose.staging.edge.yml up -d --wait

# 3. Readiness after every start (web /ready is checked by the container health check)
docker compose --env-file "$STAGING_ENV_FILE" -p avantime-staging -f docker-compose.staging.yml \
  logs web | grep -E 'cms\.warmup\.(reconciled|pages|cms_unavailable)'
npm run cms:pilot-check -w @avantime/web -- --site https://<site-host> --cms https://<cms-host>
```

With `STAGING_TLS=internal` add `-f docker-compose.staging.edge-internal-ca.yml` to every platform
command and pass `--ca <root.crt>` to `cms:pilot-check` (copy the public root from the
`staging-edge-ca` volume).

The site's `/ready` does not depend on the CMS on purpose: a CMS outage must not take the portal
down. The pilot page's own state is visible in the `cms.*` log events and in `cms:pilot-check`.

## Start order and restarts

- web starts without the CMS: the start-up reconciliation retries for about 40 s, logs
  `cms.warmup.cms_unavailable` and the page is served from the snapshot volume (see
  [CMS_PILOT.md](./CMS_PILOT.md#lost-notifications-and-staleness)).
- Strapi starts without the site: notifications to the site fail and are logged; the site
  reconciles within `CMS_CACHE_SECONDS`.
- Recreating the CMS containers keeps the database and media (named volumes). Recreating web keeps
  the snapshots; the Next.js data cache (tmpfs) is rebuilt from the CMS on start.

## Acceptance on the stand

`cms:pilot-check` covers what an anonymous visitor sees. The editor and portal paths need a browser
on the stand itself (they were rehearsed locally with the same images and compose files):

1. CMS admin over HTTPS: log in, change a text in one locale, _Save_ — the public page is unchanged.
2. _Open preview_ — draft with the yellow banner; _Выйти из предпросмотра_ returns to the published page.
3. _Publish_ / _Unpublish_ of that locale — the page follows within seconds (webhook), the other
   locales keep answering and drop/restore the locale in hreflang.
4. Media library upload — the file is served from `https://<cms-host>/uploads/…`.
5. Portal: sign-in of a test client, home, requests (create one), knowledge base, sign-out.

Strapi limits admin sign-in attempts (HTTP 429 for a few minutes after repeated logins); the portal
locks an account for 15 minutes after repeated wrong passwords regardless of the client address.

## Backups

`scripts/backup.sh` in the CMS repository writes one restore point (database dump, media archive,
content summary, per-file media checksums, manifest), encrypted with `CMS_BACKUP_ENCRYPTION_KEY`:

```bash
CMS_ENV_FILE=.env.staging CMS_COMPOSE_FILE=docker-compose.staging.yml \
  CMS_BACKUP_DIR=/var/backups/avantime-cms CMS_BACKUP_RETENTION_DAYS=14 \
  bash scripts/backup.sh avantime-cms-staging
CMS_ENV_FILE=.env.staging bash scripts/restore.sh /var/backups/avantime-cms/<stamp>   # isolated project
```

`restore.sh` restores into the separate project `avantime-cms-restore` (own volumes, loopback
ports, not on the shared network) and fails unless the restored database summary and every media
checksum match the backup.

**The CMS is not yet part of an automatic backup.** The platform's staging backup job covers only
the platform database; there is no scheduler and no durable off-host destination in this repository.
Until the DEV backup owner adds `backup.sh` to the schedule (cron/systemd timer) and puts
`CMS_BACKUP_DIR` under the host backup, CMS backups are manual. The CMS secrets (`.env.staging`) are
required for a usable restore and are backed up by the secret store, not by `backup.sh`.
