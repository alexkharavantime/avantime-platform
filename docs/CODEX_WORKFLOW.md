# Codex Workflow Avantime Platform

Этот документ определяет обязательную процедуру выполнения и завершения задач Codex в проекте Avantime. Он дополняет `AGENTS.md`, `CODEX_RULES.md` и `MASTER_SPECIFICATION.md`.

Процедура применяется ко всем задачам: анализу, разработке, исправлению ошибок, созданию документации, изменению конфигурации и подготовке Git-операций. Объём проверки должен соответствовать типу и риску задачи.

---

# 1. Подготовка к задаче

Перед началом работы Codex должен:

1. прочитать `AGENTS.md`;
2. прочитать `docs/CODEX_RULES.md`;
3. прочитать `docs/MASTER_SPECIFICATION.md`;
4. определить, какие связанные документы необходимы для задачи;
5. проверить существующую архитектуру, код и состояние Git;
6. зафиксировать ограничения пользователя;
7. не расширять область изменений без необходимости или согласования.

Для продуктовых и архитектурных задач дополнительно необходимо свериться с:

- `docs/VISION.md`;
- `docs/ROADMAP.md`;
- `docs/PRODUCT_BACKLOG.md`;
- `docs/ARCHITECTURE_2_0.md`;
- `docs/DECISIONS.md`;
- `docs/PROJECT_STATUS.md`.

---

# 2. Выполнение задачи

Во время работы Codex должен:

- выполнять изменения небольшими логическими этапами;
- сохранять существующую архитектуру и совместимость API;
- не удалять функциональность без разрешения;
- не добавлять зависимости без необходимости и объяснения;
- не изменять `.env` и deployment-настройки без разрешения;
- не помещать секреты в код, документацию, логи или Git;
- изменять только файлы, относящиеся к задаче;
- сохранять пользовательские незакоммиченные изменения;
- сообщать о найденных блокерах и рисках;
- отделять факты от предположений и экспертных оценок.

---

# 3. Техническая проверка

Для изменений кода Codex должен запустить доступные и применимые проверки:

- formatting или проверку форматирования;
- lint;
- typecheck;
- build;
- unit tests;
- integration tests;
- security tests;
- проверку миграций;
- ручную или визуальную проверку изменённого сценария.

Если проверка не запускалась, необходимо указать причину. Если ошибка не относится к текущим изменениям, это должно быть отмечено отдельно.

Для задач только по документации обязательны:

- проверка структуры Markdown;
- проверка внутренних ссылок;
- проверка фактов и терминологии;
- проверка отсутствия лишних изменений;
- проверка Git status;
- проверка того, что документ не добавлен в staged без прямого запроса.

---

# 4. Финальная проверка документации

Перед завершением работы над новым или изменённым документом Codex должен самостоятельно выполнить полную проверку.

Необходимо убедиться, что:

- документ не противоречит `VISION.md`;
- документ соответствует `MASTER_SPECIFICATION.md`;
- документ согласован с `ROADMAP.md`;
- документ согласован с `PRODUCT_BACKLOG.md`;
- документ согласован с `DECISIONS.md`, если архитектурные решения применимы;
- документ соответствует архитектурным принципам проекта;
- используется единая терминология;
- отсутствуют необоснованное дублирование и внутренние противоречия;
- структура логична и соответствует лучшим практикам архитектурной, продуктовой или технической документации;
- все обязательные разделы заполнены достаточно подробно;
- фактические показатели проверены по коду, Git или источнику истины;
- экспертные оценки явно обозначены;
- при необходимости добавлены ссылки и описаны взаимосвязи;
- последним содержательным разделом документа является «Связанные документы», если пользователь не задал иной обязательный порядок.

Если обнаружены пробелы, неоднозначности, противоречия, устаревшие решения или возможности улучшения, их необходимо описать в разделе «Рекомендации по улучшению» либо явно указать в итоговом отчёте.

Документ не должен копировать большие части других источников без необходимости. Краткая сводка допустима, если указан документ — источник подробных требований.

---

# 5. Финальная проверка архитектурных решений

При создании или изменении ADR Codex должен дополнительно проверить:

- уникальность номера;
- корректность статуса;
- наличие контекста и вариантов;
- наличие раздела «Альтернативы, которые были отклонены»;
- причины выбора;
- преимущества и недостатки;
- последствия и влияние на архитектуру;
- ссылки на связанные документы;
- связи с задачами Product Backlog;
- отсутствие изменения исторического ADR задним числом, если требуется новое решение.

---

# 6. Проверка области изменений и Git

Перед завершением любой задачи Codex должен:

1. показать изменённые файлы;
2. проверить `git status`;
3. убедиться, что не затронуты посторонние файлы;
4. проверить staged-файлы, если задача связана с подготовкой commit;
5. не выполнять commit без отдельного подтверждения;
6. не выполнять push без отдельного подтверждения;
7. предложить логичное сообщение commit;
8. сообщить о незакоммиченных изменениях, влияющих на результат.

---

# 7. Краткий итоговый отчёт

После завершения Codex должен кратко сообщить:

- что создано или изменено;
- какие файлы затронуты;
- какие ключевые решения приняты;
- какие проверки выполнены и каков их результат;
- какие ошибки или риски обнаружены;
- какие вопросы требуют дальнейшей проработки;
- какие документы рекомендуется создать следующими;
- какие существующие документы рекомендуется обновить;
- какое сообщение commit предлагается;
- что commit и push не выполнялись, если подтверждение не было дано.

Отчёт должен быть основан на фактах и не объявлять задачу завершённой, если обязательные критерии не выполнены.

---

# 8. Сокращённая команда

Фраза пользователя:

> Выполни финальную проверку согласно `CODEX_WORKFLOW.md`.

означает, что Codex обязан выполнить все применимые проверки из этого документа без необходимости повторять их в запросе.

Если пользователь задаёт более строгие или более узкие ограничения, они имеют приоритет для конкретной задачи.

---

# 9. Правила обновления workflow

- workflow пересматривается при изменении процесса разработки;
- новая обязательная проверка добавляется отдельным осознанным изменением;
- правила не удаляются без объяснения причины;
- изменения workflow должны быть согласованы с `CODEX_RULES.md`;
- workflow не должен противоречить Master Specification и ADR;
- история существенных изменений фиксируется через Git и при необходимости отдельное ADR.
