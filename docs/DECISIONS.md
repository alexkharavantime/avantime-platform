# Architecture Decision Records (ADR)

Architecture Decision Record — краткая запись значимого архитектурного решения, его контекста, рассмотренных вариантов, причин выбора и последствий.

Этот документ является официальным журналом всех важных архитектурных решений Avantime Platform. Он помогает команде понимать не только текущее устройство системы, но и причины, по которым выбран конкретный подход.

Правила ведения:

- каждое решение имеет уникальный последовательный номер;
- принятые решения никогда не удаляются;
- при изменении подхода создаётся новое ADR;
- новое решение может пометить предыдущее как `Deprecated` или `Superseded`;
- каждое ADR содержит контекст и причину принятия решения;
- каждое ADR описывает преимущества, недостатки и последствия;
- статусы и связи обновляются в том же pull request, где меняется архитектура;
- даты указываются в формате `ГГГГ-ММ-ДД`.

Каждое архитектурное решение должно содержать раздел «Альтернативы, которые были отклонены».

Цель этого раздела — сохранить историю рассмотренных вариантов и причины отказа от них.

Это позволит:

- избежать повторного анализа уже отклонённых решений;
- понимать логику принятия архитектурных решений спустя длительное время;
- быстрее вводить в проект новых участников команды;
- упрощать пересмотр решений при изменении технологий или требований.

При изменении обстоятельств ранее отклонённая альтернатива может стать основой нового ADR, при этом первоначальное решение не изменяется, а остаётся частью истории проекта.

# Формат ADR

## ADR-XXXX

**Название:** краткое название решения.

**Статус:** один из следующих:

- `Proposed` — решение предложено и обсуждается;
- `Accepted` — решение принято и обязательно для новых изменений;
- `Deprecated` — решение больше не рекомендуется, но может сохраняться в существующем коде;
- `Superseded` — решение заменено другим ADR.

**Дата:** `ГГГГ-ММ-ДД`.

### Контекст

Описание проблемы, ограничений и причин, по которым требуется решение.

### Варианты

Перечень рассмотренных вариантов.

## Альтернативы, которые были отклонены

Для каждой рассмотренной альтернативы необходимо указать:

- краткое описание;
- преимущества;
- недостатки;
- причины отказа;
- возможные условия, при которых решение может быть пересмотрено в будущем.

Если альтернатив несколько, они оформляются в виде таблицы:

| Альтернатива                  | Преимущества          | Недостатки          | Причина отказа                      | Возможность пересмотра                        |
| ----------------------------- | --------------------- | ------------------- | ----------------------------------- | --------------------------------------------- |
| Краткое описание альтернативы | Основные преимущества | Основные недостатки | Почему альтернатива не была выбрана | При каких условиях решение можно пересмотреть |

### Принятое решение

Подробное описание выбранного подхода и его границ.

### Причины выбора

Почему выбран этот вариант.

### Преимущества

Положительные последствия.

### Недостатки

Компромиссы и ограничения.

### Последствия

Что должна сделать команда после принятия решения.

### Влияние на архитектуру

Какие подсистемы, контракты и процессы затрагиваются.

### Связанные документы

Ссылки на спецификации, архитектуру, roadmap и другие ADR.

### Связанные задачи Product Backlog

Идентификаторы задач из `docs/PRODUCT_BACKLOG.md`.

## ADR-0001

**Название:** Использование Next.js App Router

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Платформе нужны публичный сайт, серверный рендеринг, защищённые кабинеты, API и единая модель маршрутов в одном TypeScript-приложении.

### Варианты

- Next.js App Router;
- Next.js Pages Router;
- отдельный React SPA и самостоятельный backend;
- другой full-stack web framework.

### Принятое решение

Использовать Next.js App Router как основную web-платформу. Страницы, layouts, middleware и route handlers размещаются по соглашениям App Router. Доменная логика не должна оставаться внутри React-компонентов или API routes.

### Причины выбора

Подход уже используется в проекте, поддерживает серверный рендеринг, metadata, вложенные layouts и серверные операции без введения второго web-стека.

### Преимущества

- единый TypeScript-стек;
- хорошая поддержка SEO;
- серверные и клиентские компоненты;
- удобная маршрутизация;
- постепенное развитие существующего кода.

### Недостатки

- требуется дисциплина границ server/client;
- обновления Next.js могут содержать несовместимые изменения;
- тяжёлые фоновые операции нельзя выполнять в пользовательском запросе.

### Последствия

Новые страницы используют App Router. Прикладная логика выносится в сервисы и репозитории. Фоновые задачи выполняются отдельными workers.

### Влияние на архитектуру

Затрагивает публичный сайт, клиентский и административный интерфейсы, API и deployment.

### Связанные документы

- `docs/ARCHITECTURE_2_0.md`;
- `docs/MASTER_SPECIFICATION.md`.

## ADR-0002

**Название:** Использование Turborepo как основы монорепозитория

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Сайт, web-приложение, UI, база данных и общие модули должны развиваться согласованно и повторно использовать код.

### Варианты

- Turborepo с npm workspaces;
- отдельные репозитории;
- Nx;
- монорепозиторий без оркестратора.

### Принятое решение

Сохранить npm workspaces и Turborepo. Приложения располагаются в `apps`, общие пакеты — в `packages`. Зависимости между workspace должны быть явными.

### Причины выбора

Решение уже внедрено, имеет низкую операционную сложность и подходит текущему масштабу команды.

### Преимущества

- повторное использование компонентов;
- согласованные изменения;
- единые проверки;
- кэширование задач;
- простая локальная разработка.

### Недостатки

- ошибки границ пакетов могут создавать скрытую связанность;
- pipeline требует поддержки;
- repository checkout со временем увеличивается.

### Последствия

Новые приложения и пакеты создаются только при ясной ответственности. Секреты и runtime-данные не размещаются в workspace.

### Влияние на архитектуру

Определяет структуру исходного кода, CI, зависимости и процесс выпуска.

### Связанные документы

## ADR-0003

**Название:** Использование PostgreSQL как основной базы данных

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Платформе требуется надёжное транзакционное хранение пользователей, организаций, обращений, знаний, документов, аудита и AI-истории.

### Варианты

- PostgreSQL;
- MySQL;
- документная база данных;
- локальные JSON-файлы;
- отдельные базы для каждого модуля с первого этапа.

### Принятое решение

PostgreSQL является обязательным production-источником истины. Локальный in-memory или файловый fallback допускается только для явно обозначенных demo-сценариев и тестов.

### Причины выбора

PostgreSQL обеспечивает транзакции, ограничения, JSON, полнотекстовый поиск и расширение `pgvector`, покрывая потребности версии 2.x.

### Преимущества

- целостность данных;
- зрелая эксплуатация;
- транзакции;
- полнотекстовый и векторный поиск;
- хорошие средства резервного копирования.

### Недостатки

- требуется управление миграциями;
- масштабирование и оптимизация требуют компетенций;
- единая база может усилить связанность модулей без репозиторных границ.

### Последствия

Все production-данные мигрируют из runtime-файлов. Каждая клиентская запись получает явную принадлежность организации.

### Влияние на архитектуру

Затрагивает все доменные модули, поиск, backup и мультитенантность.

### Связанные документы

- `docs/ARCHITECTURE_2_0.md`, раздел 8;
- `docs/ROADMAP.md`, Version 2.0.

## ADR-0004

**Название:** Использование Prisma ORM

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

TypeScript-приложению нужен типизированный доступ к PostgreSQL, миграции и согласованная схема.

### Варианты

- Prisma ORM;
- Drizzle ORM;
- прямой SQL;
- другой ORM или query builder.

### Принятое решение

Использовать Prisma для схемы, миграций и базового доступа к данным. Prisma Client инкапсулируется в доменных репозиториях; API routes и UI не обращаются к нему напрямую.

### Причины выбора

Prisma уже используется, хорошо интегрирован с TypeScript и обеспечивает единое описание моделей.

### Преимущества

- типизация;
- понятная схема;
- управляемые миграции;
- высокая скорость разработки.

### Недостатки

- сложные запросы иногда требуют raw SQL;
- генерация клиента является отдельным этапом;
- неправильное использование может привести к неэффективным запросам.

### Последствия

Миграции проходят review и тест восстановления. Для специальных возможностей PostgreSQL допускается контролируемый SQL.

### Влияние на архитектуру

Определяет слой доступа к данным и структуру пакета database.

## ADR-0005

**Название:** Использование единой дизайн-системы UI

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Публичный сайт, портал, dashboard и административная часть имеют пересекающиеся компоненты и должны восприниматься как одна платформа.

### Варианты

- единая дизайн-система и пакет компонентов;
- независимый UI каждого раздела;
- готовая внешняя библиотека без собственного слоя;
- копирование компонентов между приложениями.

### Принятое решение

Использовать единые design tokens, паттерны и пакет `@avantime/ui`. Продуктовые компоненты могут расширять систему, но не дублировать базовые элементы.

### Причины выбора

Единая система уменьшает расхождения, ускоряет разработку и повышает качество клиентского опыта.

### Преимущества

- визуальная последовательность;
- повторное использование;
- централизованная доступность;
- упрощение тем и адаптивности.

### Недостатки

- изменения общего компонента затрагивают несколько разделов;
- требуется управление версиями API компонентов;
- чрезмерно универсальные компоненты могут стать сложными.

### Последствия

Перенос текущих UI-компонентов завершается с сохранением совместимости. Все состояния компонентов документируются и проверяются.

### Влияние на архитектуру

Затрагивает `packages/ui`, стили, сайт, кабинеты и визуальные тесты.

## ADR-0006

**Название:** Использование AI Gateway вместо прямого обращения к моделям

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Сейчас OpenAI, Gemini и демонстрационный помощник вызываются разными маршрутами, что усложняет безопасность, маршрутизацию, оценку качества и контроль затрат.

### Варианты

- оставить прямые вызовы в каждом модуле;
- создать внутренний AI Gateway в модульном монолите;
- сразу выделить отдельный AI-микросервис;
- использовать только одного провайдера.

### Принятое решение

Создать внутренний AI Gateway как единственную точку вызова моделей. В Version 2.0 он остаётся модулем монолита с отдельным контрактом и может быть выделен в сервис при доказанной нагрузке.

### Причины выбора

Подход централизует политики, но не добавляет преждевременную операционную сложность.

### Преимущества

- единая авторизация;
- контроль бюджета и rate limit;
- маршрутизация и fallback;
- аудит и оценка качества;
- отсутствие provider SDK в прикладных модулях.

### Недостатки

- Gateway становится критической зависимостью;
- требуется общий контракт возможностей;
- возможна дополнительная задержка.

### Последствия

Существующие AI routes мигрируют на Gateway. Ключи, prompts и конкретные модели не размещаются в UI.

### Влияние на архитектуру

Затрагивает все AI-сценарии, безопасность, мониторинг и административные настройки.

### Связанные документы

- `docs/ARCHITECTURE_2_0.md`, раздел 2;
- `docs/ROADMAP.md`, Version 2.0.

## ADR-0007

**Название:** Поддержка нескольких AI-провайдеров

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Разные задачи, политики данных, стоимость и доступность требуют возможности использовать OpenAI, Gemini, Claude и локальные модели.

### Варианты

- один глобальный провайдер;
- несколько провайдеров через общий контракт;
- прямой выбор SDK каждым модулем;
- только локальные модели.

### Принятое решение

Поддерживать OpenAI и Gemini в Version 2.0, Claude и локальные модели — в следующих версиях. Все провайдеры реализуют общий адаптер AI Gateway. Маршрутизация учитывает возможности, стоимость, политику данных и доступность.

### Причины выбора

Это снижает vendor lock-in и позволяет выбирать модель под сценарий без изменения прикладных API.

### Преимущества

- отказоустойчивость;
- гибкость качества и стоимости;
- поддержка локальных данных;
- независимость прикладных модулей.

### Недостатки

- различия возможностей моделей;
- более сложные тесты;
- риск непредсказуемого fallback;
- больше конфигурации и мониторинга.

### Последствия

Автоматический fallback запрещается для классификаций данных, где другой провайдер не разрешён. Каждая модель проходит отдельную оценку.

### Влияние на архитектуру

Определяет AI Gateway, административные настройки, prompts, аналитику и deployment.

### Связанные документы

## ADR-0008

**Название:** Использование RAG для базы знаний

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

AI должен отвечать по проверенным материалам Avantime и клиентов, показывать источники и учитывать права доступа.

### Варианты

- ответы только из параметров модели;
- RAG по документам и статьям;
- fine-tuning для всех знаний;
- только полнотекстовый поиск без генерации.

### Принятое решение

Использовать защищённый гибридный RAG: полнотекстовый поиск, embeddings, фильтрация прав, повторное ранжирование и генерация ответа со ссылками на версии источников.

### Причины выбора

Знания часто меняются, требуют прав и должны быть проверяемыми. RAG позволяет обновлять данные без переобучения модели.

### Преимущества

- актуальные источники;
- проверяемые ответы;
- организационная изоляция;
- работа с разными форматами.

### Недостатки

- качество зависит от извлечения и индексации;
- дополнительная инфраструктура;
- риск нерелевантного контекста;
- требуется оценка качества.

### Последствия

Права проверяются до retrieval. Векторы содержат tenant-контекст и версию. Ответ без достаточных источников должен явно сообщать об ограничении.

### Влияние на архитектуру

Затрагивает AI Platform, Knowledge Center, документы, PostgreSQL, `pgvector` и фоновые задачи.

### Связанные документы

- `docs/ARCHITECTURE_2_0.md`, разделы 2 и 5;
- `docs/ROADMAP.md`, Version 2.0 и 2.2.

## ADR-0009

**Название:** Единая архитектура клиентского кабинета

**Статус:** `Accepted`

**Дата:** 2026-07-29

### Контекст

В проекте существуют основной `/portal` и экспериментальный `/dashboard` с пересекающимися сценариями и различной защитой.

### Варианты

- продолжать развивать оба пространства;
- заменить portal на dashboard одним выпуском;
- постепенно объединить их в единый портал;
- создать отдельные приложения.

### Принятое решение

Каноническим namespace клиентского кабинета является `/portal`. `/dashboard/**` сохраняется как
deprecated compatibility layer с role-aware redirects, сохранением query/deep links и без второй
оболочки навигации. Административные document operations размещаются в `/admin/documents`.

### Причины выбора

Единый кабинет уменьшает дублирование, снижает риск расхождения прав и создаёт цельный клиентский опыт.

### Преимущества

- единая навигация и сессия;
- повторное использование компонентов;
- единая модель данных;
- меньше дублирующей логики.

### Недостатки

- требуется аккуратная миграция;
- временно поддерживаются совместимые маршруты;

3. создавать осмысленные commits только после подтверждения;
4. выполнять push только после подтверждения;

- длинные feature branches создают конфликты;
- наличие `develop` отклоняется от классического GitHub Flow;

### Последствия

Прямой push в защищённые ветки запрещается. Codex не выполняет commit и push без отдельного подтверждения пользователя.

## ADR-0016

**Название:** Production persistence документов через PostgreSQL и S3-compatible storage

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

Первая итерация TASK-002 ввела tenant-aware контракты, но metadata и объекты оставались в локальной `.data`. Production требует транзакционного metadata source, горизонтально доступного object storage, проверяемой миграции и восстановления после частичного сбоя удаления.

### Варианты

- сохранить локальные JSON и filesystem в production;
- хранить metadata и бинарные объекты только в PostgreSQL;
- использовать PostgreSQL для metadata и S3-compatible private bucket для объектов;
- сразу внедрить отдельный document microservice.

### Принятое решение

Использовать PostgreSQL через `DocumentMetadataRepository` как production-источник metadata и S3-compatible private bucket через `DocumentStorage` как хранилище объектов. Конкретный S3-провайдер выбирается отдельно и не влияет на доменные/API-контракты.

Каждый database query и object key содержит server-derived `companyId`. Metadata использует составной ключ `(companyId, id)`, SHA-256 checksum и soft delete. API не удаляет объект синхронно с metadata; физический cleanup выполняется отдельной повторяемой командой.

Development сохраняет local adapters. Production configuration разрешает только PostgreSQL/S3 и работает fail-fast при неполных environment variables.

### Альтернативы, которые были отклонены

- локальный filesystem отклонён из-за отсутствия общей доступности, надёжной конкурентной записи и production backup;
- хранение PDF в PostgreSQL отклонено из-за роста базы и смешения transactional/object workloads;
- document microservice отклонён как преждевременное усложнение модульного монолита;
- немедленное hard delete отклонено из-за риска потерять metadata при частичном сбое storage.

### Причины выбора

Решение соответствует ADR-0003 и ADR-0004, сохраняет обратимые repository/storage boundaries и позволяет независимо заменить S3-провайдера. Soft delete и checksum делают миграцию и удаление проверяемыми без внедрения очереди в текущей итерации.

### Преимущества

- обязательная tenant-изоляция на database и object-key уровнях;
- PostgreSQL constraints и индексы для metadata;
- горизонтально доступное object storage;
- проверка целостности SHA-256;
- безопасный повторный migration/cleanup;
- отсутствие изменений UI и Document API contract.

### Недостатки

- требуются PostgreSQL и S3-compatible infrastructure;
- нет атомарной транзакции между database и object storage;
- cleanup пока запускается вручную;
- private bucket, encryption, versioning и backup настраиваются вне приложения;
- реальные integration tests требуют отдельного CI-окружения.

### Последствия

Deployment обязан создать private bucket с блокировкой публичного доступа, encryption, versioning и backup policy. Перед production cutover выполняются database migration, dry-run переноса, checksum verification и backup. Legacy `.data` автоматически не удаляется.

### Откат

До production cutover можно вернуть local drivers и повторить migration из неизменённой `.data`. После cutover откат требует восстановления PostgreSQL и bucket из backup либо управляемого удаления объектов и записей по migration report. Автоматический destructive rollback не допускается.

### Влияние на архитектуру

Решение затрагивает Document API, Prisma schema, deployment configuration, object storage, backup и operational cleanup, но не меняет UI, RBAC, PDF pipeline, lexical search или AI providers.

- `docs/ARCHITECTURE_2_0.md`, разделы 1 и 8;
- `docs/tasks/TASK-002.md`;
- `docs/ROADMAP.md`, Version 2.0;
- `docs/PROJECT_STATUS.md`.

## ADR-0017

**Название:** Фоновая обработка документов через queue abstraction и отдельный worker

**Статус:** `Accepted`

**Дата:** 2026-07-27

### Контекст

PDF extraction выполнялся внутри upload HTTP request. Длительная или ошибочная обработка удерживала запрос, смешивала persistence и processing, не имела управляемых retries, exclusive worker claim и quarantine. При этом TASK-002 запрещает преждевременно выбирать внешний queue provider без готовой production infrastructure.

- реализовать только in-memory background task внутри web process;
- ввести queue/worker contracts, local development adapter и отложить выбор external provider;

- выделить document processing в отдельный microservice.

| Сразу выбрать внешний provider | Production primitives и distributed locking | Требует инфраструктурного решения, deployment и отдельной зависимости       | Provider и operational environment ещё не согласованы | После выбора infrastructure и выполнения load/recovery tests |
| Отдельный microservice         | Независимое масштабирование                 | Преждевременная операционная сложность и новый deployment boundary          | Модульный монолит пока достаточен                     | При доказанной нагрузке или требованиях изоляции             |

### Принятое решение

Внутри модульного монолита определить `DocumentProcessingQueue`, `DocumentProcessingWorker` и `DocumentProcessingJob`. Upload route только сохраняет original/metadata, идемпотентно ставит job и возвращает `202`. PDF extraction выполняет отдельный worker process.

Development и тесты используют persistent `LocalDocumentProcessingQueue` с tenant-scoped file, exclusive lease и восстановлением просроченного claim. Production использует только `ExternalDocumentProcessingQueue`; конкретный adapter не входит в текущую итерацию, поэтому production processing работает fail-fast до его подключения.

Metadata является source of truth для lifecycle: `UPLOADED`, `QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`, `QUARANTINED`, `DELETED`. Все переходы проверяются централизованно и выполняются conditional repository update с обязательным tenant.

### Причины выбора

Решение немедленно убирает тяжёлую работу из HTTP, формирует стабильный provider-neutral контракт и позволяет проверить idempotency, retries, quarantine, tenant isolation и restart safety без преждевременного инфраструктурного выбора.

### Преимущества

- короткий upload HTTP lifecycle;
- идемпотентная постановка job;
- exclusive processing и восстановление lease;
- централизованные retries и quarantine;
- обязательный tenant и checksum;
- возможность подключить внешний provider без изменения API/worker domain logic;
- сохранение модульного монолита.

### Недостатки

- local adapter не поддерживает distributed multi-process locking;
- production processing недоступен до реализации external adapter;
- нет heartbeat/lease extension для очень долгих job;
- process supervision, queue metrics и alerts ещё не выбраны;
- один worker process обрабатывает один явно настроенный tenant.

### Последствия

- web и worker deploy/process lifecycle разделяются;
- production deployment обязан предоставить внешний queue adapter и не может использовать local queue;
- retries выполняются только для классифицированных временных ошибок;
- provider messages, stack traces, secrets и document content не попадают в клиентские ответы и worker logs;
- quarantine operations остаются `ADMIN`-only и single-document;
- OCR, embeddings и hybrid RAG строятся поверх этого worker boundary в следующих итерациях.

### Откат

До production cutover можно остановить worker и сохранить queued metadata/job для повторного запуска. Возврат synchronous extraction не рекомендуется. Для code rollback новая metadata schema остаётся совместимым superset, но статусы новых документов нужно предварительно нормализовать; destructive автоматический rollback не выполняется.

### Влияние на архитектуру

Решение затрагивает Document API, metadata repository, Prisma schema, development runtime data, operational commands и deployment configuration. UI меняется только для отображения новых статусов. AI providers, lexical search, portal/dashboard boundaries и RBAC не меняются.

## ADR-0018

**Название:** Изолированная инфраструктурная валидация Document subsystem

### Влияние на архитектуру

**Название:** Provider-neutral OCR boundary поверх tenant-aware document worker

**Статус:** `Accepted`

**Дата:** 2026-07-28

### Контекст

## ADR-0020

**Название:** PostgreSQL/pgvector, deterministic hybrid ranking и server-generated citations

**Статус:** `Accepted`

**Дата:** 2026-07-28

### Контекст

TASK-004 требует tenant-aware semantic retrieval без отдельной vector infrastructure, безопасную смену embedding model/version и проверяемые citations. Существующий lexical search должен сохраниться, а retrieval и provider calls не могут доверять client-supplied tenant или citation IDs.

### Варианты

- оставить только lexical search;
- использовать отдельную vector database;
- хранить vectors в PostgreSQL/pgvector;
- заменить lexical search semantic retrieval;
- применить детерминированное weighted merge или отдельный neural reranker;
- принимать citations из ответа модели или строить их server-side.

### Принятое решение

Использовать `pgvector` в существующем PostgreSQL. Vector record имеет составную tenant/document/chunk/model/version identity и переменную dimension с SQL constraint. Поиск всегда фильтрует tenant, document lifecycle, active embedding model/version/dimensions до выдачи результата.

Сохранить lexical и semantic retrievers как независимые contracts. Первая hybrid-реализация нормализует их scores, применяет конфигурируемые weights, deduplicate и ограничение chunks на документ. Neural reranker не добавляется до получения production measurements.

Citation IDs создаёт сервер после повторной проверки metadata и chunk в текущем tenant. Модель получает только immutable source IDs и недоверенные excerpts; неизвестные markers удаляются.

### Причины выбора

- PostgreSQL уже является system of record и прошёл integration/migration gates;
- `pgvector` сохраняет транзакционную и tenant-aware модель без нового operational boundary;
- deterministic merge воспроизводим в regression/evaluation tests;
- server-generated citations не позволяют модели или клиенту подменить источник.

### Преимущества

- одна backup/access-control boundary;
- безопасная совместимость model/version/dimensions;
- lexical fallback и объяснимые score components;
- идемпотентная индексация changed chunks;
- проверяемая tenant isolation и citation provenance.

### Недостатки

- variable-dimension storage пока не использует ANN index;
- PostgreSQL принимает дополнительную retrieval load;
- качество weighted merge ограничено без production relevance data;
- page range зависит от provenance upstream extractor.

### Последствия

- integration PostgreSQL использует image с `pgvector`;
- migration rehearsal проверяет extension, tables, indexes и dimension constraint;
- production требует `pgvector`, PostgreSQL embedding jobs и настроенные AI providers;
- отдельная vector database, ANN strategy и neural reranker требуют нового решения на основании load/evaluation data;
- reindex ограничен одним tenant/document и является dry-run по умолчанию.

### Альтернативы, которые были отклонены

- отдельная vector database отклонена как преждевременная инфраструктурная сложность;
- semantic-only retrieval отклонён из-за потери точных терминов и существующего lexical поведения;
- client/model-generated citations отклонены из-за риска forgery и cross-tenant references;
- массовый destructive reindex отклонён из-за операционного риска;
- neural reranker отложен до измеримого качества baseline.

### Влияние на архитектуру

Затрагивает Document metadata/migrations, AI Gateway, background jobs, Knowledge Center, health, operations и evaluation. TASK-002/TASK-003 processing и OCR boundaries остаются независимыми.

## ADR-0021

**Название:** Redis как production coordination и queue adapter

**Статус:** `Accepted`

**Дата:** 2026-07-28

### Контекст

TASK-002–TASK-004 оставляли document queue local, embedding queue в PostgreSQL и

- общий fencing механизм для двух workers;
- отсутствие content в queue.

### Недостатки

- Redis становится критическим coordination dependency;
- reconciliation после полной потери Redis требуется отдельно;
- custom Lua scripts требуют contract/integration tests.

### Последствия

Workers обязаны проверять fence при critical updates. Потеря Redis блокирует новые
AI/queue operations; lifecycle восстанавливается из PostgreSQL.

### Влияние на архитектуру

Document/embedding workers становятся отдельными scalable processes. Public API,
tenant/RBAC и document storage contracts не меняются.

## ADR-0023

**Название:** PostgreSQL append-only AI usage ledger и locked budget reservations

**Статус:** `Accepted`

**Дата:** 2026-07-28

### Контекст

In-memory operational events TASK-004 не позволяют агрегировать затраты,
идемпотентно сверять usage или предотвращать concurrent overspend.

### Варианты

- оставить in-memory events;
- хранить ledger/budgets в Redis;
- PostgreSQL append-only ledger и reservations;
- внешний billing SaaS как source of truth.

### Альтернативы, которые были отклонены

| Альтернатива | Преимущества     | Недостатки                     | Причина отказа             | Возможность пересмотра |
| ------------ | ---------------- | ------------------------------ | -------------------------- | ---------------------- |
| Memory       | Нет migration    | Теряется, нет race safety      | Не production-ready        | Только tests           |
| Redis ledger | Быстрые counters | Не durable billing record      | Redis не system of record  | Для derived cache      |
| Billing SaaS | Готовые отчёты   | Vendor/data boundary и latency | Нет утверждённого provider | Как downstream export  |

### Принятое решение

Хранить tenant-scoped `AiUsageLedger`, `AiBudgetPolicy` и
`AiBudgetReservation` в PostgreSQL. Reservation под advisory lock учитывает
daily/monthly/provider limits до provider call. Reconciliation append-only и
идемпотентна; основная валюта — EUR. Content, prompts, answers и vectors запрещены.

### Причины выбора

PostgreSQL уже является tenant-aware system of record и предоставляет
transaction/locking primitives для race-safe hard stop.

### Преимущества

- durable daily/monthly aggregation;
- concurrent overspend protection;
- idempotent usage;
- одна backup/audit boundary.

### Недостатки

- provider cost сначала оценочный;
- advisory locking добавляет database contention;
- lifecycle reservations требует cleanup/monitoring.

### Последствия

## ADR-0024

**Название:** Exact pgvector search по умолчанию; ANN только после threshold gate

**Статус:** `Accepted`

**Дата:** 2026-07-28

### Контекст

TASK-004 использует exact cosine search с tenant/lifecycle filters. TASK-005
сравнила exact, IVFFlat и HNSW на controlled synthetic dataset. ANN нельзя
включать без измеримого latency/recall выигрыша и понятной rebuild strategy.

### Варианты

- оставить exact search;
- включить IVFFlat;
- включить HNSW;
- выделить отдельную vector database.

### Альтернативы, которые были отклонены

| Альтернатива       | Преимущества         | Недостатки                                       | Причина отказа               | Возможность пересмотра                           |
| ------------------ | -------------------- | ------------------------------------------------ | ---------------------------- | ------------------------------------------------ |
| IVFFlat сейчас     | Небольшая p50 выгода | Recall@K 0.2667 на проверке                      | Не прошёл recall threshold   | При tuning/larger representative dataset         |
| HNSW сейчас        | Recall 1.0           | Медленнее exact и индекс больше на малом dataset | Нет измеримого выигрыша      | При p95 exact выше SLO на production-like volume |
| Separate vector DB | Независимое scaling  | Новый tenant/backup/operations boundary          | Нет доказанной необходимости | При исчерпании PostgreSQL strategy               |

### Принятое решение

Сохранить exact search default. Controlled dataset: 3 tenants, 10 documents на
tenant, 20 chunks на document, 32 dimensions, 60 queries, concurrency 6.

Результаты:

| Strategy | p50 / p95 / p99 ms    |     QPS | Recall@K | Index bytes |
| -------- | --------------------- | ------: | -------: | ----------: |
| Exact    | 2.620 / 5.185 / 5.935 | 1679.28 |   1.0000 |       81920 |
| IVFFlat  | 2.427 / 3.765 / 4.089 | 1800.56 |   0.2667 |      507904 |
| HNSW     | 2.691 / 4.538 / 5.124 | 1526.54 |   1.0000 |      368640 |

ANN gate: representative dataset, tenant-filtered recall at least 0.95, p95
latency improvement at least 30%, no leakage/timeouts and acceptable index/build
cost. Index is added by a separate additive migration, built/rebuilt with
documented concurrency and can be dropped without changing stored vectors.

### Причины выбора

Exact is fastest/smallest enough for measured volume and preserves full recall.
Synthetic measurements do not justify operational complexity.

### Преимущества

- no recall degradation;
- simple migration/backup/rebuild;
- tenant filters remain exact and inspectable.

### Недостатки

- exact search may not scale to production volume;
- test does not measure production CPU/memory or real embedding distribution;
- future ANN migration remains required when thresholds are crossed.

### Последствия

CI runs only a bounded smoke test. Larger controlled runs are operational,
isolated and clean up their temporary table/index. Sequential scans and timeouts
remain recorded metrics.

### Влияние на архитектуру

PostgreSQL/pgvector remains the vector boundary; no new service or schema index is
enabled in this task.

### Решения для ежегодного пересмотра

Ежегодно желательно пересматривать:

- набор и качество AI-провайдеров;
- стоимость и маршрутизацию моделей;
- стратегию локальных LLM;

- актуальность плагинной и интеграционной стратегии.

Принятое ADR не меняется задним числом. Результат ежегодного пересмотра фиксируется новым ADR, если подход изменился.

### Поддержание журнала в актуальном состоянии

1. Назначить владельцем журнала ведущего архитектора.
2. Создавать ADR до реализации значимого архитектурного изменения.
3. Связывать ADR с задачей Product Backlog и pull request.
4. Проверять последствия решения при review.
5. Обновлять статус только через отдельное осознанное изменение.
6. Не удалять устаревшие решения.
7. При замене указывать взаимные ссылки между старым и новым ADR.
8. Ежеквартально проверять Proposed-решения и планируемые темы.
9. Ежегодно проводить полный архитектурный обзор.

Главный принцип: ADR должен оставаться кратким источником ответа на вопрос «почему система устроена именно так», а не превращаться в дубликат технической документации.
